# Changelog

All notable changes to this project are documented in this file.
Format based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/).

## [1.2.0] — 2026-09-24

### Fixed
- **Ventoy install log full of `[33m…[0m` garbage, and shown twice**: `Ventoy2Disk.sh` colors its output with ANSI escape codes, which the wizard's log displayed raw, and the output was appended both by a progress callback and again at the end. Codes are now stripped and the output appears once.
- **After a Ventoy install, the drive wasn't found again until it was replugged**: the drive list was refreshed while the kernel was still re-reading the new partition table. The refresh now waits for udev to settle. A refresh that finds no drive also no longer keeps showing the previous one in the info panel and ISO table.
- **Table header labels didn't line up with their columns**: the header row hardcoded its own fixed column widths, while each data row stretched its filename column to fill the remaining space instead of using the same fixed widths — so every column after it (local/latest version, status) drifted further out from under its header label the wider the window got. Both now share the exact same column widths.
- **Only the first download in a batch showed progress in the main window**: `_do_download` fired the "hide the progress bar" cleanup and the "move on to the next queued item" callback as two separate, independently scheduled steps. Both landed in the same Tk event queue, but in an order that raced: the next item's own "show progress" (triggered by moving on) got processed first, immediately followed by the *previous* item's leftover "hide progress" — undoing it right away. Every download after the first one in a queue proceeded with its progress silently invisible. Fixed by bundling both into a single callback, so hiding and moving on can never be reordered against each other.
- **CachyOS and EndeavourOS logo sync always failing**: CachyOS's `favicon.ico` URL now 404s into an HTML page instead of an actual icon (`cannot identify image file`), and EndeavourOS's logo URL pointed at a 2021 upload path that's gone from the site entirely (plain `HTTP 404`) — both silently broken any time "Download missing logos" ran. Both projects now serve their current mark as `/favicon.svg` instead; rasterized locally from that (their real, current logos: CachyOS's "C", EndeavourOS's mountain peak) and bundled under `assets/logos/`, same as Debian/Fedora/Ubuntu/Hiren's above.
- **Hiren's BootCD PE logo an unrecognizable grey blur**: the project has no real icon of its own beyond a plain text wordmark, so it fell back to its site's `favicon.ico` — a 16×16 disc silhouette that turned to mush once scaled up to the sizes this app actually displays. Replaced with a crisp, high-resolution "handyman" (crossed wrench/hammer) glyph from Google's Material Symbols (Apache-2.0), colored and rasterized locally, which reads clearly at every size and fits the tool-belt nature of the ISO — a proper Windows PE-based repair/recovery toolkit rather than a distro.
- **No way to remove an ISO before checking it for updates**: the 🗑 delete button only rendered once a `CheckResult` existed for the row — i.e. after "Check all" (or that row's own check) had run at least once. A freshly scanned drive showing only "Pending" rows had no delete button at all, so removing an unwanted ISO meant running an update check first just to make the button appear. It's now always shown regardless of check status.
- **Memtest86+ downloaded but never actually usable from the Ventoy menu**: the open-source build's only distribution format on memtest.org is a `.zip` wrapping the real `.iso` — the app downloaded and dropped that `.zip` straight onto the drive as-is, matching its own recognition pattern (so it read as "installed" in the list) while Ventoy can only boot ISO/IMG/WIM/VHD(x)/EFI files, never a raw zip archive, leaving a dead, unbootable file. Fixed generically in the download layer: any downloaded `.zip` whose sole member is a `.iso`/`.img` is now transparently unwrapped right after download, replacing the zip on disk with the actual bootable image. Downloading a second time into a folder that already had one also produced a mangled name like `mt86plus_..._x86_64.iso_1.iso`: the existing-file disambiguation logic only knew about single extensions, so "`name.iso.zip`" got a `_1` spliced in as "`name.iso_1.zip`" before unwrapping ever saw it — fixed to treat `.iso.zip`/`.img.zip` as one compound extension, landing the suffix before it (`name_1.iso.zip`) instead of inside it. Unwrapping never overwrites an image already on the drive under the same name either: it gets a `_1`, `_2`... suffix instead.
- **Outdated Fedora logo, and an Ubuntu one with the wordmark baked in**: Fedora's still came from a years-old third-party mirror, and Ubuntu's showed the "ubuntu" text crammed into the icon — both unreadable at the 32px this app actually renders logos at. Replaced with each project's current official icon-only mark (Fedora's 2021 "f" mark, Ubuntu's 2022 solid Circle of Friends, no text), rasterized from their real vector artwork at high resolution and bundled locally under `assets/logos/`, same treatment as the Debian/Zorin fix below.
- **Outdated Zorin OS logo, and a Debian one that read poorly at icon size**: Zorin's icon still used its pre-2022 glossy blue orb branding — replaced with the current flat "Z" mark from zorin.com's own site. Debian's used a third-party crop (swirl + "debian" text squeezed into a non-square image) that got blurry at the small sizes this app actually renders logos at — replaced with Debian's own official icon-only swirl asset (`openlogo-nd`, no text) from debian.org, which stays legible at 32px.
- **A single mouse wheel notch scrolling all the way to the bottom/top of scrollable lists** (the ISO download picker, the theme editor's image/icon tabs, the theme manager, the logo browser, the main ISO table): traced to `customtkinter.CTkScrollableFrame` itself — on Linux it scrolls by `-event.delta` "units" with no scaling at all, assuming `delta` is already a small number, which doesn't hold on every desktop (some GNOME/Wayland setups report much larger values). Patched its global wheel handler to always scroll by one unit per event regardless of `delta`'s magnitude — matching how the X11 `Button-4`/`Button-5` wheel events (unaffected by this) already behave — and normalized this app's own redundant per-dialog wheel bindings to the same fixed step.
- **Installed Ventoy version not shown for a just-installed drive**: version detection only read `ventoy/ventoy_release`/`ventoy/ventoy.json` from the main partition — but on a fresh install, that file genuinely doesn't exist yet (Ventoy's own installer confirms this: `get_disk_ventoy_version()` in its own `ventoy_lib.sh` reads the version from the sibling `VTOYEFI` partition instead, never from the main one). Fixed by falling back to the plain `VENTOY_VERSION="x.y.z"` line already sitting in `VTOYEFI`'s own `grub.cfg` — mounting that partition briefly to read it, and unmounting it right back, since it's still never meant to be presented as a manageable drive.
- **A just-installed Ventoy drive reported as "no Ventoy drive detected"**: the scanner only recognized a drive as Ventoy by the presence of its own `ventoy/` folder — but on a fresh install that hasn't been booted from yet, that folder doesn't exist: it's Ventoy's *own* internal boot partition (always labeled `VTOYEFI`) that holds all the boot/control files at install time, not the main data partition where the user's ISOs go. It also needed the drive to already be mounted, which — after this app's own auto-unmount-before-install step, or Ventoy2Disk.sh's own unmounting mid-install — it usually isn't right after a fresh install, normally requiring an unplug/replug for the desktop to remount it. Fixed on both fronts: a drive is now also recognized by a sibling `VTOYEFI` partition on the same disk, and the data partition of a hotplugged disk that carries a `VTOYEFI` partition gets auto-(re)mounted, without ever presenting `VTOYEFI` itself as a manageable drive (it holds Ventoy's own boot payload, not ISOs). The `VTOYEFI` label is read from `lsblk` without mounting anything, so unrelated USB drives the user left unmounted are never touched. Drive detection also now runs off the UI thread, so it can't freeze the window.
- **Reinstalling Ventoy on a drive that already has it was a dead end**: `Ventoy2Disk.sh` refuses a plain install ("already contains a Ventoy with version ..., use -I to force it") the moment the disk isn't blank — which the USB-drive picker can't always detect beforehand, since it only recognizes an existing Ventoy install while the drive happens to be mounted. The app had no way to pass Ventoy2Disk.sh's `-I` (force) flag at all, so hitting this left nothing to do but close the dialog. It now recognizes this specific message and offers to force the reinstall instead.
- **Drive list crashing with `PermissionError: [Errno 13] Permission denied: '/run/media/root'`**: the USB-drive scanner's fallback path walks two levels into `/media`, `/run/media` and `/mnt` when `/proc/mounts` doesn't have what it needs, with no guard against another user's mount subdirectory it can't read into — including one created moments earlier by a root-elevated Ventoy install run via `pkexec`, which is exactly how this got hit. Every "Actualiser" click, and the automatic rescan right after a successful Ventoy install, crashed outright. Fixed by skipping any directory this process can't access instead of letting the exception propagate.
- **Ventoy installation failing with "/dev/sdX is already mounted, please umount it first!"**: `Ventoy2Disk.sh` refuses to run at all on a mounted device, and the target USB drive is normally still mounted right when the install button is clicked (the app just scanned it). Fixed by unmounting it automatically first (via `udisksctl` when available, with a couple of retries — an auto-mounting desktop can otherwise silently remount it right back). If something still has it open (e.g. a file manager window browsing the drive) and it truly can't be unmounted, the app now says so plainly and stops there instead of running the install script anyway and dumping its raw failure into the log.
- **"Create a Ventoy drive" window clipped at the bottom, hiding the Install button**: the dialog had a fixed, non-resizable `620x520` size. Its actual content already needs ~644px at normal (1x) UI scaling, and every widget grows further on a higher DPI/scaling setting — a common case on Linux desktops — so the Install/Close buttons at the bottom could end up entirely off-window with no way to resize and reach them. Fixed by sizing the window from its actual required height at startup and making it resizable, so it now always opens tall enough to show every button, and can still be resized further if needed.
- **Downloaded Ventoy forgotten every time the "Create a Ventoy drive" wizard was reopened**: the download went to a throwaway `tempfile.mkdtemp()` directory that only the running dialog instance knew about. Closing the wizard and reopening it (or even just letting the OS clean `/tmp`) made it report "Ventoy not found locally" again, forcing a full re-download — and, since nothing then re-selected the USB drive relationship automatically, it could look like the download "did nothing" even though it had actually just repeated itself. Fixed by downloading into a persistent cache (`~/.local/share/ventoyisoupdater/ventoy/`) that both the download step and the "already installed?" check now look at, so a previously downloaded copy is found immediately and the Install button is ready right away. Since that cache is writable by the user and its script is run as root, the cached copy is never executed as-is: right before each install, the release archive kept in the cache is re-checked against the official SHA256 published by the Ventoy project and extracted into a fresh private temp dir, which is what actually runs. If it can't be verified (offline, modified archive), the install is refused and a fresh download is requested.
- **Ventoy installation silently doing nothing on Linux**: `Ventoy2Disk.sh` always asks "Continue? (y/n)" on stdin before wiping the disk (twice, for a plain install), and has no flag to skip it. The app ran it without ever answering that prompt, so depending on how stdin was inherited it either hung until the 2-minute timeout, or hit EOF immediately, read that as "no", and exited with status 0 — which the app then reported as a **successful** install even though the disk was never touched. Fixed by feeding the confirmation automatically (the same warning is already shown to the user beforehand, in the app's own confirmation dialog), and raised the timeout to 180s.
- **Ventoy installation always failing on Linux**: the code looked for the installer script as `ventoy2disk.sh`, but the official Ventoy Linux archive ships it as `Ventoy2Disk.sh` (mixed case). On any case-sensitive filesystem (ext4, btrfs, xfs — i.e. virtually every Linux distro, Fedora included) the lookup never matched, so `find_ventoy_in_dir`/`find_ventoy_binary` always returned nothing and the app reported "Ventoy2Disk.sh not found" even right after downloading and extracting a fresh copy. Fixed by matching the real filename (both cases now accepted, as a third-party package could still use the lowercase form).

### Added
- **ISO file size column** in the main table, between the filename and the local version — reads it straight off the file on disk, formatted like the rest of the app (MB for a small tool like Memtest86+, GB for a regular distro ISO).
- **The "Download an ISO" picker now refreshes itself after a batch finishes**: the left-hand distro list's installed state (✓, highlighted) was computed once when the dialog opened and never updated — downloading one or several ISOs left the list showing them as *not* installed until the whole dialog was closed and reopened. It now re-scans the drive right after a batch completes, updating both the distro list and the just-downloaded version's own button (back to "add" instead of staying stuck on "already queued").
- **Select several ISOs and download them all in one go**: the "Download an ISO" picker used to start a download and close itself the moment you clicked a version. It now lets you add versions — from any number of distros — to a queue before downloading anything, shown in a panel with a remove button per entry; "Download all" then runs through the queue one download at a time instead of you repeating the whole picker flow for every ISO.
- **"Manage the theme" no longer a dead end on a drive with no theme yet**: the button was flat-out disabled whenever `ventoy/ventoy.json` didn't exist — which nothing creates automatically, so it never existed on a freshly installed, never-booted drive. It's now always enabled, and offers to bootstrap a theme before opening the editor: not a bare empty file, but Ventoy's own bundled sample theme (background, menu/scrollbar pixmaps, a few icons) pulled from the same release archive the app already downloads to install Ventoy, so there's an actual working theme to look at and tweak from the start.
- **Omarchy** (opinionated Arch Linux + Hyprland desktop by DHH): checks GitHub releases (`omacom/omarchy`) for the version, builds the ISO URL from `iso.omarchy.org`, and verifies it against the official `.sha256` sidecar. 65 distribution checkers now, 124 registered variants.
- **"Copy" button on the Ventoy install log**: the output of `Ventoy2Disk.sh` (or the error that stopped it) can now be copied to the clipboard directly from the "Create a Ventoy drive" wizard, instead of having to select the wrapped text by hand.

### Changed
- **Downloads are now always organized as `<category>/<distro>/`** (e.g. `linux/Alpine Linux/`, `tools/Memtest86+/`, `security/Kali Linux/`): category folders used to be reused only if they already existed, so a fresh drive ended up with one flat folder per distro at its root, and security/BSD/gaming/server distros could fall back into an existing `linux/` folder. A folder already holding ISOs of the same distro still takes priority, so existing layouts are left alone. Distro names are also turned into valid folder names (`Pop!_OS (Intel/AMD)` used to create two nested folders).
- **Confirmation/error/info popups now match the app's dark theme**: every one of them (~25 call sites) went through `tkinter.messagebox`, which always renders with the OS's native Tk look — light background, native buttons — clashing with the rest of the UI. Replaced with a themed `CTkToplevel`-based dialog (`gui/dialogs.py`) styled like the rest of the app, with a colored icon per severity (info/warning/error/question) and a red accent on destructive confirmations (deleting a file, wiping a USB drive).

## [1.1.1] — 2026-08-23

### Fixed
- **Logo download failing for 4 distros** (Kali, AlmaLinux, Manjaro, Nobara): `logo_url` pointed to an `.svg` file, a format PIL can't decode at all — every logo sync attempt failed with a raw `cannot identify image file` error, for every user, every time. Fixed by bundling a real PNG for each under `assets/logos/` (same mechanism already used for Proxmox/Pop!_OS) instead of depending on a vector URL.

## [1.1.0] — 2026-08-22

### Added
- **ARM64 support alongside x86_64** for 13 distributions whose upstream source publishes a genuine, generic, Ventoy-bootable ARM64 ISO (not a device-specific SBC image): Proxmox VE, AlmaLinux, CentOS Stream 9/10, Rocky Linux, Debian, FreeBSD, Gentoo, openSUSE Tumbleweed, Kali Linux, Oracle Linux, Alpine Linux, Void Linux (glibc+musl), Ubuntu Server. x86_64 stays the priority default everywhere; each ARM64 build appears as its own clearly labeled `(ARM64)` entry, never mixed with its x86_64 counterpart. 123 registered variants, up from 108.

### Fixed
- **Void Linux (glibc)**: the filename pattern no longer matched the real files the checker itself downloads (missing the `-base`/`-xfce`/etc. suffix) — local version detection was silently broken.
- **CentOS Stream 9/10**: the x86_64 filename pattern was broad enough to also match an aarch64 file sitting on the same USB drive, defeating the point of telling the two architectures apart.

## [1.0.1] — 2026-08-22

### Fixed
- **Proxmox VE**: the upstream directory now lists an arm64 ISO (`proxmox-ve_9.2-1-arm64.iso`) alongside the regular amd64 build. The filename regex only avoided matching it by accident (no explicit architecture anchor) — hardened to explicitly reject any filename containing `arm`.
- Same fix also deduplicates matches: the source page repeats each filename several times (link, size, date), which previously produced 5–10 duplicate entries per version in the version browser.

### Internal
- Every code comment, docstring, and diagnostic log message translated to English (previously French-first). No effect on the app's UI or behavior — the French/English toggle for what the *user* sees is untouched.
